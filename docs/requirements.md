# 要件定義書 — PD Forge（仮称）

> パブリックドメイン（PD）IP を活用し、AI コーディング支援で「実用ライトアプリ」を作成・公開・販売できるプラットフォーム

- ドキュメントバージョン: 0.1（ドラフト）
- 最終更新: 2026-05-31
- ステータス: レビュー前ドラフト

---

## 1. 背景・目的

### 1.1 背景
- AI コーディング（自然言語からのコード生成）の普及により、個人がアプリを作るハードルが急速に下がっている。
- 2024〜2026 年にかけて Steamboat Willie 版 Mickey（1928）、Betty Boop 初期版、Nancy Drew 初期作などが米国でパブリックドメイン入りし、合法的に利用できる「知名度の高い IP 素材」が増えている。
- 一方で、中小・個人クリエイターが「公式（または PD）の IP を安全に使って収益化できる」プラットフォームは空白地帯になっている。
- ゲーム寄りの UGC（Roblox 等）は存在するが、**日常的に使うライトな実用アプリ（タスク管理・習慣・カレンダー等）× IP × 収益化**という領域は手薄。

### 1.2 目的
- PD IP を合法的・安全に使い、AI 支援で実用ライトアプリを作成できる環境を提供する。
- 作成したアプリをマーケットプレイスで公開・販売し、クリエイターが収益を得られるようにする。
- プラットフォームは **月額サブスクリプション + 販売手数料** を主収益とする。
- 将来的に PD IP から「中小・公式 IP のライセンス開放」へ拡張するための基盤を作る。

### 1.3 スコープ方針
- 初期（MVP）は **実用ライトアプリ（タスク管理・習慣トラッカー・カレンダー・メモ）** に限定。ゲームは対象外。
- 作成方式は **ノーコードではなく AI コーディングベース**（生成されたコードを編集・プレビュー可能）。
- **モバイル中心（モバイルファースト）**。エンドユーザーが日常的に使うツールのため、スマホでの利用体験を最優先に設計する。
- 初期市場は **北米（英語）先行**。日本展開は後続フェーズ。

### 1.4 アプリ配信モデル（重要な設計判断）
日常使いのモバイルアプリを「ユーザー生成（UGC）」として大量に扱うため、**各アプリを個別にネイティブとして App Store / Google Play に公開する方式は採らない**（審査・開発者アカウント・更新コストが UGC では非現実的）。代わりに以下を採用する。

- **コンテナ（スーパーアプリ）方式を基本とする**:
  - 自社が単一の「ホストアプリ」を App Store / Google Play に公開。
  - クリエイターが作成したアプリは、ホストアプリ内のサンドボックスで動作する**バンドル（コード/設定）**として配信・更新する。
  - これによりストア審査を毎回通さずに即時公開・更新が可能（OTA 更新）。
- **PWA（インストール可能な Web アプリ）を併用**:
  - ストア外配布が可能で、ストア手数料を回避できる。
  - ホーム画面追加・通知・オフライン対応で「普段使い」要件を満たす。
- ネイティブ機能（プッシュ通知・ウィジェット・カレンダー連携等）はホストアプリ側が API として提供し、各アプリから利用させる。

> この方式により、(1) ストア手数料の回避、(2) 即時更新、(3) 審査の一元化、(4) コスト構造の安定化、を同時に狙う。詳細なトレードオフは「13. 未決事項」を参照。

## 4. ビジネスモデル / 収益要件

### 4.1 収益源

| 収益源 | 内容 | 価格イメージ | 優先度 |
|---|---|---|---|
| プラットフォーム月額（主） | アプリ作成・PD アセット利用・AI 機能・公開/販売 | Basic $19/月、Pro $39/月 | 最高 |
| アプリ販売手数料 | マーケットプレイス販売額からの徴収 | 20–25% | 高 |
| POD グッズ連携 | アプリデザインのグッズ化 | 15–20% | 中（Phase 2） |
| Enterprise/教育プラン | チーム・教育機関向け | $99〜/月 | 中 |

- クリエイターの収益サイクル: 月額支払い → AI でアプリ作成 → マーケットプレイスで販売 → 月額を回収＋利益。
- 透明性要件: 手数料率・収益分配・利用制限をダッシュボードで明示。

### 4.2 コスト構造（COGS / 変動費）

モバイル普段使い前提では、コストが **「クリエイター数」だけでなく「エンドユーザーの日次利用」** に比例する点が最大の論点。主なコスト項目と性質は以下。

| コスト項目 | 性質 | ドライバー | 備考・対策 |
|---|---|---|---|
| AI 生成（LLM トークン） | 変動・最大の不確実性 | アプリ生成・修正の回数/規模 | プロンプトキャッシュ、差分生成、プラン別の生成回数上限、テンプレート活用で圧縮 |
| アプリ実行ホスティング（コンテナ/PWA） | 変動 | **エンドユーザー MAU・リクエスト数** | 静的配信＋エッジ/サーバレスで単価最小化。重い処理はクライアント側に寄せる |
| データ保存・同期（DB/ストレージ） | 変動 | 保存アプリ数・ユーザーデータ量 | 無料枠の範囲を明確化、超過は従量課金 or 上位プラン |
| 審査・モデレーション | 半固定（人件費） | 公開申請数 | AI 自動審査で一次フィルタ、人手は例外対応に限定 |
| 決済手数料 | 変動 | 売上・課金額 | Stripe 約 2.9%+30¢ を価格に織り込む |
| ストア手数料 | 条件付き変動 | アプリ内課金経由の売上 | **サブスクは Web 課金で回収しストア 15–30% を回避**（コンテナ/PWA 方針と整合） |
| POD 原価・物流 | ほぼパススルー | グッズ販売 | 原価は購入者負担、プラットフォームは手数料のみ |
| 固定費 | 固定 | — | 人件費・基盤・サポート・法務 |

### 4.3 ユニットエコノミクスの考え方

- **粗利の式（クリエイター単位/月）**: `月額 + 手数料収入 − (AI 生成コスト + 当該クリエイターのアプリのホスティング/保存コスト + 決済手数料 + 審査按分)`。
- **守るべきガードレール**:
  - 1 クリエイターあたりの **AI 生成コストが月額の一定割合（例: 30%）を超えない** よう、プラン別に生成回数・モデルを制御する。
  - エンドユーザー利用が増えるほどホスティングコストが増えるため、**人気アプリの収益（販売/将来の広告/投げ銭）がホスティング増分を上回る** 設計にする。無料配布アプリが大量利用される「赤字テール」を上限・レート制限で抑制。
- **価格・プラン設計への示唆**:
  - Basic/Pro の差は主に **AI 生成枠・公開アプリ数・利用できるモデル/機能** で切る。
  - ヘビーユーザー向けに従量（クレジット）課金 or 上位プランを用意し、コスト超過分を回収。
  - サブスク課金は可能な限り Web 経由にして、ストア手数料を構造的に回避。
- **要試算（Phase 0 で確定）**: 代表的なクリエイター/アプリの (a) 平均生成トークン量と単価、(b) アプリあたり月間エンドユーザー数とリクエスト単価、(c) 1 アプリあたり保存データ量 — の 3 指標から損益分岐を算出する。

## 5. 機能要件

優先度: ◎ = MVP 必須 / ○ = MVP 推奨 / △ = Phase 2 以降

### 5.1 AI アプリ生成（コア）◎
- 自然言語プロンプトからアプリのコードを生成（例: 「1928 Steamboat Willie Mickey を使ったタスク管理アプリを作って。完了したらアニメーションで褒めて」）。
- 生成対象スタック: **モバイル向けを第一級でサポート**。コンテナ方式で動作する形式（React Native ベース、もしくは PWA）を標準出力とする。
- リアルタイムプレビュー: **スマホ実機/エミュレータでの即時プレビュー**（QR でホストアプリに読み込み、OTA 反映）。
- 追加プロンプトによる修正（「キャラを Betty Boop に変更」「もっと可愛く」）。
- 生成履歴・バージョン管理。
- コードエディタ（Cursor / Copilot 風）での手動編集。

### 5.2 PD キャラクターライブラリ ◎
- 厳選 PD アセット 10〜15 個を MVP 搭載（Steamboat Willie Mickey 1928/1930、Betty Boop 初期、Nancy Drew 初期、Einstein/Tesla/da Vinci 等）。
- 各アセットに画像・簡易アニメーション・セリフ集を付与。
- 各アセットに**スタイルガイド / 利用ルール**（商標回避、「1928 PD Version」明記、後期デザイン混入禁止）を紐づけ。
- 実在人物（Einstein 等）は「Historical Figure based on...」明記＋大幅変形を必須化。

### 5.3 サブスクリプション / 課金 ◎
- 認証・課金（Stripe）。
- プラン: Basic / Pro の 2 種。
- 利用制限（AI 生成回数、アプリ公開数等）をプランごとに設定。

### 5.4 公開・マーケットプレイス ◎（簡易版）
- 作成アプリの公開機能。
- 一覧・検索・詳細ページ。
- 購入・ダウンロード（初期は Web アプリ形式）。
- 販売額からの手数料自動徴収。
- レビュー・人気ランキング（○）。

### 5.5 管理ダッシュボード ◎
- 作成アプリ一覧、編集・公開状態管理。
- 収益ダッシュボード（売上・手数料・支払い）。
- 使用 PD アセットの利用履歴（法的証跡）。

### 5.6 審査・安全性 ◎
- AI 自動チェック（商標混同、キャラクター崩れ、禁止表現）。
- 公開前の人間審査ワークフロー（初期は運営目視）。
- 公開物への自動表記（「Based on the 1928 Public Domain version...」「AI 支援度」バッジ）。

### 5.7 透明性バッジ ○
- 各アプリに「PD バージョン使用」「AI 使用度 / 人間編集度」を表示。

### 5.8 Phase 2 以降 △
- 個別アプリのネイティブ単体公開（必要な人気アプリのみ、コンテナとは別ルートで）。
- バックエンド機能（ユーザー認証・データ永続化）の高度化。
- POD グッズ連携。
- 多言語対応。
- コラボレーション機能、分析ダッシュボード。
- 中小・公式 IP のライセンス開放（収益分配モデル）。

## 6. 非機能要件

| 区分 | 要件 |
|---|---|
| パフォーマンス | AI 生成は非同期、プレビューは即時反映。生成待ち時間の可視化。 |
| スケーラビリティ | クラウド前提（Vercel / AWS）。生成物ストレージとモデレーションを分離。 |
| 可用性 | MVP では 99% 程度を目標。決済・認証は外部 SaaS に依存。 |
| セキュリティ | 認証/認可、決済情報は Stripe に委譲（PCI 非保持）、シークレット管理。 |
| プライバシー | GDPR / CCPA 対応（同意管理、削除要求対応）。 |
| 可監査性 | PD アセット利用履歴・審査ログを保持（法的証跡）。 |
| 多通貨/税 | グローバル決済・VAT 等の税対応（段階的）。 |
| アクセシビリティ | ライト/ダークモード、モバイル閲覧対応。 |

## 7. 法務・コンプライアンス要件（最重要）

- **PD の地域差管理**: 米国基準で PD のものを中心に扱い、他地域ユーザーには注意喚起。地域制限/警告の実装を検討。
- **商標・パブリシティ権回避**:
  - Disney（Mickey）、Fleischer（Betty Boop）等の残存商標に注意。
  - 「1928 Public Domain Version」「Historical Figure based on...」を必須明記。
  - AI による大幅変形（カートゥーン/アニメ化）を推奨/必須化。
  - 実在人物の利用は「教育・風刺・変形」に限定。
- **AI 生成物の表示**: 人間貢献度表示・AI ラベル（米 / EU AI Act 等への対応）。
- **DMCA / Takedown 体制**: 迅速な削除フローと窓口。
- **利用規約・免責**: 利用者責任の明記、IP 専門・国際対応の弁護士レビューを前提。

## 9. ユーザー体験フロー（MVP）

1. サインアップ → 月額登録
2. PD ライブラリ閲覧 → キャラ選択
3. プロンプト入力 → AI がコード生成
4. プレビュー確認 → 追加プロンプト/手動で微調整
5. 審査（AI 自動 + 必要に応じ人間）通過
6. マーケットプレイスに公開
7. 他ユーザーが購入 → 収益発生 → ダッシュボードで確認

## 13. 未決事項 / 要確認

- 事業名の最終決定（PD Forge / CodeLegacy / Chronicle 等の候補あり）。
- 配信モデルの確定: **コンテナ（スーパーアプリ）方式 + PWA 併用** を基本方針としたが、(a) ストア規約（特に Apple の UGC/コード実行・サブスク課金ルール）への適合性、(b) コンテナ vs 各アプリ PWA 単独 のどちらを主にするか、の最終判断が必要。
- ストア手数料回避のためのサブスク課金経路（Web 課金 / リーダーアプリ例外の活用）の可否確認。
- 生成 AI モデルの選定と **コスト試算**: 代表クリエイター/アプリの平均生成トークン量・単価、アプリあたりエンドユーザー MAU とリクエスト単価、保存データ量 から損益分岐を算出（Phase 0）。
- プラン別の利用制限（AI 生成回数・公開アプリ数・モデル）と従量課金（クレジット）の設計。
- 審査の人手リソースとスケール時の自動化度合い。
- 初期 PD アセット 10〜15 個の最終リストと各スタイルガイドの中身。
